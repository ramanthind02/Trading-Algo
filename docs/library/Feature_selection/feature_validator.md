# Feature Validator — Unified Validation Framework

> **Status:** Library specification (single source of truth)
> **Purpose:** Systematic validation pipeline for continuous and rule-based features with EDA, binning diagnostics, parameter sensitivity, and permutation testing.
> **Last updated:** 2026-02-13

---

## Motivation

Feature validation in systematic trading requires rigorous statistical testing to prevent overfitting and ensure robustness. The Feature Validator provides a unified framework that guides researchers through four critical validation phases:

1. **Exploratory Data Analysis (EDA)** — Understand feature distributions, temporal stability, and basic diagnostics
2. **Binning Model Fitting** — For continuous features, validate that binning successfully identifies tradeable regions
3. **Parameter Sensitivity Analysis** — Identify stable parameter regions using grid-aware smoothing and visual inspection
4. **Permutation Testing** — Statistically validate that features exhibit genuine predictive power, not random chance

**Key design principles:**

- **Separation of concerns**: Continuous and rule-based features follow distinct pipelines where their characteristics differ
- **Researcher-in-the-loop**: Provide rich diagnostics and visualizations; researcher makes final decisions
- **Pre-specified thresholds**: Metrics and thresholds must be set *before* seeing data to prevent data snooping
- **Composable reports**: Each phase generates structured reports that can be inspected independently or combined

---

## Feature Types

The Feature Validator supports two distinct feature families, each with specialized handling:

### Continuous Features

**Definition:** Raw continuous indicator values (e.g., RSI, momentum, volatility ratios) that require binning to identify tradeable regions.

**Validation approach:**
- **EDA**: Distribution analysis, decile plots, temporal stability
- **Binning diagnostics**: Validate that quantile binning identifies consecutive bins exceeding pre-specified thresholds
- **Parameter sensitivity**: Grid-aware neighbor smoothing to identify stable parameter regions
- **Permutation testing**: Vector shuffle → feature shuffle → candle shuffle (progressively stronger nulls)

**Reference:** [Continuous Binning Specification](features/Continuous_binning.md)

---

### Rule-Based Features

**Definition:** Discrete signals (-1, 0, +1) generated by rule logic (e.g., breakout above threshold, regime filters).

**Validation approach:**
- **EDA**: Level distribution, per-level statistics, transition matrices
- **No binning phase**: Features are already discrete
- **Parameter sensitivity**: Same grid smoothing as continuous features
- **Permutation testing**: Candle shuffle only (preserves rule serial correlation)

**Reference:** [Rule-Based Features Specification](features/rule_based.md)

## Pipeline Phases

### Phase 1: Exploratory Data Analysis (EDA)

**Purpose:** Provide researcher with comprehensive diagnostics to understand feature behavior before statistical testing.

**Execution:** Run EDA *per parameter combination* independently. Each param combo receives its own EDA report.

#### Common EDA (both feature types)

**Descriptive statistics:**
- Feature distribution: min, max, mean, median, std, skew, kurtosis
- Target distribution: same metrics for returns
- Missing data: count and percentage of NaNs
- Sample size per regime/period

**Temporal stability:**
- Time series plot: feature and target over time (identify regime changes, structural breaks)
- Rolling correlation: feature-target correlation in rolling windows (e.g., 252-day) to detect stability/drift

**Correlation analysis:**
- Feature-target correlation: Pearson, Spearman, Kendall
- Lagged correlations: test for lead/lag relationships

**Rolling objective metric:**
- Rolling window computation of user-specified objective metric (e.g., Sharpe, Sortino, mean return)
- Window size: user-customizable (default: 252 days for daily data)
- **Rolling objective plot**: Visualize metric stability over time
- Purpose: Detect regime changes, drift, or periods of degradation/strength

---

#### Continuous Feature EDA (additional)

**Decile analysis:**
- Bin feature into **15 quantile bins** (default, user-customizable)
- Per-bin statistics:
  - Mean target return
  - Volatility (std of returns in bin)
  - Sharpe ratio: `mean / std`
  - t-statistic: `mean / (std / sqrt(N))`
  - Sample count
- **Decile plot**: Visualize mean return, Sharpe, and t-stat across bins
- **Monotonicity test**: Check if bins show monotonic trend (Kendall's tau)

**Distribution plots:**
- Histogram: feature distribution with quantile overlays
- Q-Q plot: compare feature to normal distribution
- Kernel density estimate (KDE)

---

#### Rule-Based Feature EDA (additional)

**Per-level statistics:**
- Mean return, volatility, Sharpe, adjusted Sharpe for each level (-1, 0, +1)
- Bootstrap confidence intervals (95%) for mean returns
- **Level plot**: Bar chart showing performance by level

---

#### EDA Output

**Format:** Structured `EDAReport` dataclass containing:
- All computed statistics
- Plot objects (matplotlib Figure or file paths)
- Diagnostic flags (warnings, red flags)

**Separate reports per param combo:** If testing RSI with lookbacks [10, 14, 20], generate three independent EDA reports.

**Reference:** Existing EDA infrastructure in `eda/eda_runner.py`

---

### Phase 2: Binning Model Fitting (Continuous Features Only)

**Purpose:** Validate that the binning pipeline successfully identifies tradeable regions (consecutive bins exceeding threshold).

**Applies to:** Continuous features only. Rule-based features skip this phase (already discrete).

#### Process

1. **Fit binning model** using [Continuous Binning Specification](features/Continuous_binning.md):
   - Quantile binning (15 bins default)
   - Compute per-bin Sharpe and adjusted Sharpe
   - Detect contiguous regions of bins exceeding threshold
   - Apply t-stat filter (|t| > 2.0)
   - Merge consecutive bins into trading zones

2. **Customization by researcher:**
   - **Objective metric**: Sharpe, Sortino, mean return, etc.
   - **Metric threshold**: Pre-specified value (e.g., Sharpe > 0.5)
   - **t-stat threshold**: Default 2.0 (can adjust for exploratory vs production)
   - **Minimum region width**: Default 2-3 bins (reject isolated spikes)

3. **Success criteria:**
   - At least one contiguous region identified
   - Region meets minimum width requirement
   - Bins in region exceed both metric threshold and t-stat threshold

#### Binning Diagnostics Report

**Key metrics:**
- Number of regions identified
- Feature ranges covered by each region
- Per-region statistics: mean Sharpe, adjusted Sharpe, t-stat, sample count
- **Shape detection**: Tail (touches extreme bin) vs hump (surrounded by neutral bins)
- **Coverage**: Percentage of feature distribution covered by tradeable zones

**Diagnostic plots:**
- Bin heatmap: color-coded by Sharpe/t-stat
- Region boundaries overlaid on feature distribution
- Position multiplier curve: show continuous scaling function

**Failure modes:**
- No regions identified → feature may lack structure
- Only isolated single-bin spikes → likely noise, not robust signal
- Regions fail to exceed threshold → insufficient edge

**Output:** `BinningDiagnosticsReport` with pass/fail verdict and detailed diagnostics.

### Phase 3: Parameter Sensitivity Analysis

**Purpose:** Identify stable parameter regions using grid-aware neighbor smoothing. Distinguish genuine signal (broad stable regions) from overfitting (isolated parameter peaks).

**Applies to:** Both continuous and rule-based features.

**Input:** DataFrame of grid-search results — multiple parameter combinations with their performance metrics.

#### Grid-Aware Neighbor Smoothing

**Concept:** For each parameter combination, compute a **smoothed objective** by averaging with 1-step neighbors in the parameter grid.

**Formula:**
```
smoothed_objective(P) = mean([objective(P)] + [objective(N) for N in neighbors(P)])
```

**Neighbor definition:** 1-step axis-aligned neighbors (differ in one parameter dimension by one grid step).

**Example (1D grid):**
```
RSI lookback: [10, 14, 20, 30]

For lookback 14:
  neighbors = {10, 20}
  smoothed_Sharpe = (Sharpe_10 + Sharpe_14 + Sharpe_20) / 3
```

**Stability ratio:**
```
stability_ratio = smoothed_objective / raw_objective
```

- **High ratio (> 0.8)**: Parameter is in a stable region
- **Low ratio (< 0.5)**: Isolated peak, likely overfit

**Reference:** [Grid Search Parameter Stability](stability/grid_search_parameter_stability.md)

---

#### Interactive Visualizations

**1D parameter grids:**
- Line plot: raw vs smoothed objective
- Shaded regions: stability ratio > 0.8

**2D parameter grids:**
- Heatmap: raw objective surface
- Contour plot: smoothed objective surface
- Overlay: highlight stable regions (stability ratio > 0.8)

**3D+ parameter grids:**
- 2D slices (fix one parameter, plot others)
- Scatter plot: raw vs smoothed objective with color-coding

**Interactive features:**
- Hover: show exact values, stability ratio, neighbors
- Click: select parameter combo to see detailed stats
- Zoom: inspect specific parameter regions

**Implementation:** Use existing `eda/parameter_analysis.py` (`ParameterAnalyzer` class) and `metrics/plotting/parameter_plots.py`.

---

#### Output

**ParameterSensitivityReport:**
- Per-parameter raw and smoothed objectives
- Stability ratios
- Identification of stable regions (contiguous params with stability ratio > 0.8)
- Interactive plots (Plotly or Bokeh for web-based inspection)
- Recommendations: which parameter combos are in stable regions

### Phase 4: Permutation Testing

**Purpose:** Statistically validate that feature performance is better than chance using progressively stronger null hypotheses.

**Applies to:** Both continuous and rule-based features.

**Framework:** Three-stage sequential testing as specified in [In-Sample Permutation Testing](permutation_testing/in-sample_pt.md).

**Pipeline behavior (early stopping):**
- Tests are run **sequentially** per parameter combination
- If a param combo **fails** an earlier stage, it is **excluded** from later stages (saves computation)
- Only param combos that pass Stage 1 proceed to Stage 2
- Only param combos that pass Stage 2 proceed to Stage 3 (walkforward stability)
- This creates a funnel: many params enter Stage 1, fewer survive to Stage 2, even fewer reach Stage 3

---

#### Stage 1: Vector Shuffle (Quick Filter)

**Null hypothesis:** No relationship between feature values and target returns.

**Procedure:**
- Shuffle the **fitted feature vector** (binned output or rule output)
- Preserve target order
- Recompute objective metric (e.g., Sharpe)
- Repeat 500–1000 times to build null distribution

**Pass criterion:** Observed objective > 90th percentile of null distribution (α = 0.10)

**Scope:** Per parameter combination.

**Output:** `VectorShuffleReport` with p-value, critical value, pass/fail verdict.

---

#### Stage 2: Pipeline Permutation (Rigorous Test)

**Continuous features:**

**Option A (feature shuffle, quick screen):**
- Shuffle raw continuous feature vector (before binning)
- Run full binning pipeline on shuffled feature
- Same threshold and region detection rules

**Option B (candle shuffle, recommended stronger null):**
- Shuffle bars (candles) in time
- Recompute bias-node feature from shuffled bars
- Run full binning pipeline
- **Destroys temporal structure** (autocorrelation, momentum runs)

**Rule-based features:**
- **Candle shuffle only** (shuffling rule output would create unrealistic rapid flipping)
- Shuffle bars → recompute rule → evaluate

**Pass criterion:** Same as Stage 1 (α = 0.10)

**Scope:** Per parameter combination.

**Output:** `PipelinePermutationReport` with p-value, critical value, pass/fail verdict.

---

#### Stage 3: Walkforward Stability Analysis

**Purpose:** Assess temporal consistency of optimal parameter regions (not a permutation test, but a stability diagnostic).

**Procedure:**
1. Divide in-sample data into non-overlapping walkforward folds (e.g., 2-year chunks)
2. For each fold independently:
   - Evaluate **all** parameter combinations (need full grid for neighbor smoothing)
   - Compute smoothed neighbor metric
   - Select top-K parameter combos (e.g., K = 3)
3. Compare across folds: are the same parameter combos consistently in top-K?

**Stable feature (good):**
```
Fold 1: top-3 = {RSI_4, RSI_5, RSI_3}
Fold 2: top-3 = {RSI_5, RSI_4, RSI_10}
Fold 3: top-3 = {RSI_4, RSI_5, RSI_3}
Fold 4: top-3 = {RSI_5, RSI_4, RSI_10}
→ Consistent neighborhood around RSI_4-5
```

**Unstable feature (bad):**
```
Fold 1: top-3 = {RSI_4, RSI_5, RSI_3}
Fold 2: top-3 = {RSI_20, RSI_14, RSI_10}
Fold 3: top-3 = {RSI_3, RSI_2, RSI_4}
Fold 4: top-3 = {RSI_14, RSI_10, RSI_20}
→ Jumping across parameter space, likely noise
```

**Output:** `WalkforwardStabilityReport` with per-fold top-K selections, consistency metrics, stability verdict.

**Reference:** [In-Sample Permutation Testing § 3](permutation_testing/in-sample_pt.md#3-walkforward-stability-analysis)

## Researcher Ensemble Formation (Manual Decision)

**After all four phases**, the researcher reviews:
1. EDA reports → understand feature behavior
2. Binning diagnostics (continuous only) → validate binning success
3. Parameter sensitivity report → identify stable regions
4. Permutation test results → statistical significance per param combo
5. Walkforward stability report → temporal consistency

**Selection criteria (pre-committed):**
- Parameter must **pass permutation tests** (Stage 1 and 2)
- Parameter must appear in **stable region** (sensitivity analysis stability ratio > 0.8)
- Parameter must appear in **top-K across 3+ folds** (walkforward stability)

**Ensemble formation:**
- Select 2–10 parameter combinations from stable neighborhood
- Simple mean aggregation of member signals
- High correlation within ensemble is expected (parameter smoothing, not redundancy)

**Reference:** [In-Sample Permutation Testing § 4](permutation_testing/in-sample_pt.md#4-researcher-ensemble-formation)

## Vault Integration (Feature Persistence)

**Purpose:** Save validated features to the Vault system for production deployment and ensemble construction.

**When to save:** After the researcher is satisfied with all validation phases and has formed the ensemble.

### Saving Features to Vault

**Process:**
1. Researcher completes all validation phases (EDA, binning diagnostics, parameter sensitivity, permutation testing)
2. Researcher forms ensemble from validated, stable parameter combinations
3. For each selected parameter combination:
   - Fit the base model (`BaseModel` with `BinningModel`) on full in-sample data
   - Save to vault using `base_model.save_to_vault(ensemble_dir)`
   - Model ID is auto-generated from binning hyperparameters

**Vault structure:**
```
vault/
└── {timeframe}/                    # e.g., D, W, M
    └── {ensemble_name}_{direction}/  # e.g., commodity_breakout_long
        └── features/
            └── {feature_column}.json  # e.g., rsi_signal_D_lookback_14.json
```

**Example workflow:**
```python
from feature_selection.base_models import BaseModel, QuantileBinningModel
from utils.enums import TimeFrame, Direction

# After validation, create ensemble directory
ensemble_dir = create_ensemble_directory(
    vault_root='vault',
    timeframe=TimeFrame.D,
    ensemble_name='momentum_strategy',
    direction=Direction.LONG
)

# Save each validated parameter combination
for param_combo in validated_params:  # e.g., RSI lookback [3, 4, 5]
    # Create binning model with validated hyperparameters
    binning_model = QuantileBinningModel(
        n_bins=15,
        selection_metric='sharpe',
        strategy='long'
    )

    # Define bias node spec
    bias_spec = {
        'module_name': 'rsi',
        'timeframes': [TimeFrame.D],
        'params': {'lookback': param_combo}
    }

    # Create and fit base model
    base_model = BaseModel(
        bias_node_spec=bias_spec,
        binning_model=binning_model,
        ticker=Ticker.ES
    )
    base_model.fit(candles_df, target_data)

    # Save to vault (model ID auto-generated)
    model_id = base_model.save_to_vault(ensemble_dir)
    print(f"Saved: {base_model.feature_column}::{model_id}")
```

**Key points:**
- **One feature file** per feature column (e.g., `rsi_signal_D_lookback_14.json`)
- **Multiple model variants** per feature (different binning hyperparameters)
- **Auto-generated model IDs** (e.g., `quantile_binning_15`)
- **Strategy matching** enforced: long models → long ensembles only

**Validation:**
- Vault validates strategy/direction match on save
- Feature column naming must match timeframe
- Duplicate model IDs rejected (same hyperparameters)

**Reference:** [Vault User Guide](../Vault/vault_user_guide.md) for detailed vault operations and management.

## Configuration and Defaults

**User-configurable:**
- Number of bins (default: 15)
- Objective metric (Sharpe, Sortino, mean return, etc.)
- Metric threshold (pre-specified before seeing data)
- t-stat threshold (default: 2.0)
- Minimum region width (default: 2-3 bins)
- Rolling metric window size (default: 252 for daily, 52 for weekly)
- Permutation replicate count (default: 500–1000)
- Significance level α (default: 0.10 for exploratory, 0.05 for production)
- Walkforward fold structure (e.g., 2-year chunks)
- Top-K for walkforward stability (default: 3)

**Non-negotiable:**
- All thresholds must be **pre-specified** (no data snooping)
- Same threshold for original and permuted data
- Consistency across features (don't tune per feature)
- **Early stopping in permutation tests**: failed params don't proceed to later stages
